## 1. 项目用途

### 它是什么

一个 **Windows 桌面视觉识别自动化工具**。核心循环：

```
截屏（全屏 或 指定窗口区域）
  → OpenCV 灰度多尺度模板匹配（在 PNG 模板库中查找目标元素）
  → 模拟鼠标点击 / 键盘按键 / 拖曳
  → 按「步骤队列」或「蓝图连线」决定下一步
```

### 解决什么问题

把**重复的图形界面操作**编排成可重复执行的任务流程。用户不需要目标程序提供任何
API 或插件——只要有屏幕像素就能操作。

### 适用场景

- 游戏日常任务挂机（从预设名「追放每日任务」「追放主线关卡」「追放周回」判断，
  原始目标是某款名为「追放」的手游）
- 任何"必须在 GUI 里反复点同样位置"的重复劳动
- **前提**：目标程序允许模拟鼠标键盘输入

### 它明确不是什么

- ❌ 不是 RPA 框架，没有 API/脚本注入能力
- ❌ 没有 OCR、没有颜色匹配
- ❌ **完全依赖图像识别，识别不到就没有兜底手段**

### 安全提示

脚本会**实际移动鼠标并发送键盘输入**。运行期间不要将重要文件、设置界面或需要
人工确认的窗口置于可能被误点击的位置。第一次测试务必关闭「循环执行」。

### 4.4 单步执行的数据流（一次 `execute_task` 内部）

```
execute_task(task, stop_flag, log_callback)
  ├─ 按 type 分派：
  │    condition / switch / event / delay / keyboard_move
  │    key_press / drag / click_until_gone → 各自的专用函数
  └─ 默认（normal / advanced）：
       ├─ 若 click=True 且 click_requires_match=False 且有固定点击点
       │    → 直接点击，不识别
       └─ while True 识别循环：
            ├─ screen_img = capture_screen()
            ├─ results = match_task_templates(...)   ← 已完成按名过滤
            ├─ advanced 用 find_leftmost_match，normal 用 find_first_match
            ├─ 命中 →
            │    ├─ 决定点击坐标（优先「记录点击点」，否则识别中心转全局坐标）
            │    ├─ click_global_position(...)
            │    ├─ 按 wait_for 等待结果（time / disappear / next_appear / change_then_appear）
            │    ├─ 等待失败 → 返回 timeout 跳转 或 {"execution_state":"timeout"}
            │    ├─ 成功后检查 detour_success_jump_to → 返回 {"outer_jump_to": n}
            │    └─ 否则返回 True
            └─ 未命中 →
                 ├─ 若配置了迂回 → execute_detour_task(...)
                 ├─ 超时 → 按 timeout_jump_to 跳转 / 作为可选步骤跳过 / 抛 RuntimeError
                 └─ interruptible_sleep(poll_interval) → 继续下一轮
```

### 5.2 关键耦合点

1. **`config.py` 被双向使用**：既是配置文件又是运行期可变状态。
   `gui_pyside6.py` 在每次开始执行前**原地改写** `config.TARGET_WINDOW_TITLE` /
   `USE_WINDOW_MODE`，且**停止后不还原**。

2. **`tasks.py` 的模块级全局是隐式共享状态**：
   `TASKS` / `USER_PRESETS` / `PRESET_METADATA` / `DELETED_PRESET_NAMES` /
   `TASK_PRESETS` 全部在 **import 时求值**。
   GUI 用 `TASKS[:] = deepcopy(...)` **原地替换**来保持对象同一性
   （`main.py` 持有同一个 list）。

3. **`CaptureOverlayMixin` 的钩子契约**（重要）：
   两个窗口的差异集中在「数据访问路径」与「收尾动作」两点，通过钩子注入：

   | 钩子 | PySide6ScriptWindow | BlueprintWindow |
   |---|---|---|
   | `_capture_index()` | `self.current_task_index` | `self.current_index` |
   | `_capture_task_list()` | 全局 `TASKS` | `self.tasks`（副本）|
   | `_capture_after_task_changed()` | `save_current_tasks()` + `refresh_task_list()` | `_push_history()` + `refresh()` + `save_layout()` |
   | `_capture_show_parent()` | 无操作（无父窗口）| `parent.show()` |
   | `_capture_log()` | 写日志框 | 丢弃 |
   | `_group_metadata_for_current_mode()` | `mode_group_metadata[当前预设]` | `self.group_metadata`（副本）|
   | `_group_default_color()` | `#e0f2fe` | `#38bdf8` |

   **新增共享方法时，优先复用这些钩子，不要复制两份实现。**

4. **`nodes.py` 的接口只用了一部分**：
   - 被使用：`NodeGraph.validate()` / `to_payload()`、`normalize_task()`、
     **`remap_jump_targets()`（跳转重编号的单一维护点）**
   - **从未被调用**：`NodeGraph.from_payload()`、`reachable_indices()`、
     `tasks_to_nodes()`、`TaskNode.execute()`

5. **双寻址系统**（最重要的架构事实）：

   | 连接类型 | 存储字段 | 寻址方式 |
   |---|---|---|
   | 普通顺序连接 | `flow_next` | **节点 UUID 字符串** |
   | 所有分支跳转 | `detour_jump_to` / `detour_success_jump_to` / `timeout_jump_to` / `condition_*` / `switch_default_jump_to` / `loop_*` / `event_*` | **1-based 步骤序号（整数）** |

   ⚠️ 序号 = **在完整 TASKS 列表中的位置**（含被禁用的步骤）。运行时通过
   `_outer_step_number` 还原对应关系。

   **任何改变步骤下标的操作都必须调用 `nodes.remap_jump_targets()`**。
   此前该逻辑散落在多处且覆盖度不一致（10 / 10 / 2 / 0 个字段），
   导致拖动排序会静默破坏现有任务——**已修复**，现有 6 个调用点。

## 9. 当前代码设计

### 9.1 架构类型判定

**没有套用标准架构模式**（不是 MVC / MVP / MVVM）。实际是：

> **分层架构（Layered）+ 面向对象（GUI 层）+ 面向过程（引擎层）的混合体**

| 层 | 组成 | 特征 |
|---|---|---|
| **表现层** | `gui_pyside6.py` + `capture_overlay.py` + `blueprint_canvas.py` + `task_widgets.py` + `ui_common.py` | 面向对象。两个窗口类留在 gui_pyside6；`CaptureOverlayMixin` 与采集覆盖层在 capture_overlay；画布 QGraphics 组件在 blueprint_canvas；`ui_common` 是纯辅助叶子模块 |
| **应用/引擎层** | `main.py` | **面向过程**，全是模块级函数，通过参数与回调与 GUI 交互 |
| **适配层** | `nodes.py` | 面向对象（`Node`/`TaskNode`/`NodeGraph`）+ 纯函数（`remap_jump_targets`）|
| **数据层** | `tasks.py` | 面向过程 + 模块级全局状态 |
| **能力层** | `core/*` | 面向过程，无状态，**不依赖任何 GUI** ✅ |
| **配置层** | `config.py` | 模块级常量（运行期被改写 ⚠️）|

### 9.2 关键模式

| 模式 | 用在哪 | 评价 |
|---|---|---|
| **分层 + 单向依赖** | 整体 | ✅ `main.py` 不反向依赖 GUI |
| **Mixin + 模板方法** | `CaptureOverlayMixin` | ✅ 本次新增，消除 738 行重复 |
| **回调/观察者** | `run_task_queue` 的 7 个 callback 参数 | ✅ 解耦得当 |
| **信号槽（Qt）** | `TaskWorker` | ✅ 线程安全的正确做法 |
| **适配器** | `TaskNode` | ⚠️ 设计意图正确，但**只用了一半** |
| **双寻址** | `flow_next`(UUID) vs `*_jump_to`(序号) | ⚠️ 现在有单一重编号入口，风险已控制 |
| **全局可变单例** | `tasks.TASKS` / `config.*` | ❌ 隐含耦合 |

### 9.3 一句话总结

**架构骨架是对的**（分层清楚、引擎与 GUI 解耦、急停设计扎实、共享实现已抽出），
**主要遗留问题是全局可变状态与双寻址系统**——但双寻址的风险已通过
`remap_jump_targets()` 单一维护点控制住，且它只影响那 5 种未使用的节点。

> 本次构建时的环境限制：系统 `site-packages` 与用户目录都不可写，
> 因此改用 `python -m venv --system-site-packages <临时目录>\vf_build_env`
> 建了一个临时环境，在其中装 PyInstaller（`--no-cache-dir`）后构建。
> **这不是项目需求**，只是绕开权限限制的手段；正常机器直接 `pip install pyinstaller` 即可。
> 该临时环境与构建中间物都在 `%TEMP%` 下，**不进工程目录、不进版本控制**。

> **一键脚本（2026-10-01）**：`打包.bat`（等价于 `python build_package.py`）把
> 「预检 → 构建 → 部署 → 校验」串起来，内部调用的就是上面这条命令。它额外解决四个实测踩过的坑：
> 中间物不落进工程目录；部署时**只替换程序部分**、分发目录里的 4 个数据文件逐字节保留
> （部署前后逐个比对哈希）；构建后检查"必须保留"的 `Qt6Svg.dll` + `qsvg.dll`、
> `opengl32sw.dll`、`tkinter`、模板库是否都在位；分发版正在运行时拒绝部署（文件被占用会半途失败）。
> 支持的开关：`--zip`、`--sync-data`、`--build-only`、`--from-dist <已有产物>`、`--keep-work`。
> 校验不通过返回非 0（`2` 预检 / `3` 构建 / `4` 校验）。

### 为什么是 `onedir` 而不是 `onefile`

`onefile` 每次启动都要把整包解压到 `%TEMP%\_MEIxxxx`（本产物 202.8 MB，用户会明显感到启动延迟，
且频繁的自解压行为容易被杀软/SmartScreen 拦）。`onedir` 只在构建时展开一次，启动即时、
目录结构可查（排查“图标没进去 / 插件丢了”必须能看到文件）。
同理，4 个 JSON 与模板库落在 exe 同级可写目录，**exe 不能放在 `C:\Program Files`**。

### 体积账（实测）

| 项 | 数值 |
|---|---|
| 本机 `Qt6*.dll` 合计 | 316.2 MB / 144 个 |
| 其中与本项目无关的模块 | **277.5 MB / 115 个**（`Qt6WebEngineCore.dll` 单个 194.0 MB）|
| 排除无用 Qt 模块后 | 249.0 MB |
| 再二次裁剪 C++ DLL | **202.8 MB**（砍掉 Qt 声明式 UI 链 + PDF + TUIO + ffmpeg）|
| 主要体积来源 | `cv2.pyd` 67.7 MB、`numpy` 相关 19.4 MB、`Qt6Core/Gui/Widgets` 25.2 MB、`opengl32sw.dll` 19.7 MB、`PIL\_avif` 7.5 MB |

**排除项（`excludes`）**只挡 Python 绑定，挡不住 PyInstaller 通过二进制依赖分析带进来的
C++ DLL，所以规格里另有一层 `_DROP` 过滤（每次构建会打印裁掉了哪些文件）：

- `Qt6VirtualKeyboard.dll` → `Qt6Quick.dll` → `Qt6Qml.dll` → `Qt6Network.dll`…
- `plugins\imageformats\qpdf.dll` → `Qt6Pdf.dll`；`plugins\generic\qtuiotouchplugin.dll` → `Qt6Network.dll`
- `opencv_videoio_ffmpeg4120_64.dll`（27.0 MB）：全项目 0 处 `VideoCapture`/`VideoWriter`

**故意保留**：`Qt6Svg.dll` + `plugins\imageformats\qsvg.dll`（勾选框 SVG 样式，缺了勾选框就是空白）、
`opengl32sw.dll`（19.7 MB，GPU 驱动不可用时的软件 OpenGL 兜底，删了在虚拟机/远程桌面上可能黑窗）、
`PIL\_avif*.pyd`（7.5 MB，收益太小、不值得多一个变量）。

### 三个实测拦下来的坑（改规格前必读）

| 坑 | 证据 | 后果 |
|---|---|---|
| **绝不能排除 `tkinter`** | `pyautogui` 导入期就 `import mouseinfo`，而 `mouseinfo/__init__.py` 在 Windows 分支的 `import tkinter` **没有** try/except（`pymsgbox` 那个有保护，我看走眼过一次）| `core/input.py` 的 `import pyautogui` 直接 `ModuleNotFoundError` → **程序启动即失败** |
| **`--add-data "icons;icons"` 是必需的** | `config.ICON_DIR` ← `paths.resource_root()` ← frozen 时 = `sys._MEIPASS` = `<dist>\_internal` | 少了它模板库全空、识别全失效；另外 Windows 分隔符是 `;`，写错成 `:` 不报错但静默不带资源 |
| **`--noconsole` 后 stdout/stderr 静默失效** | 实测 stdout/stderr 置 `None` 后 `print(x, file=sys.stderr)` **不抛异常也不输出** | 与 §8.2 #7（日志不落盘）叠加 → 接收方遇到问题**拿不到任何证据** |

### 分发前仍未解决的事项

1. **数据层会让接收方首次运行就受挫**：预设 `追放主线关卡` 第 11 步 `template='captured_baef8b3b2c_copy'` 的 PNG 不存在；
   当前任务列表 4 步引用 `shop_daily`/`guild_daily`/`monthly_card`/`side_road`（PNG 不存在，且 `templates_for_names` 是**静默忽略**）；
   当前列表第 1 步 `wait_for='next_appear'` 却没有 `next_template` → `main.py` 会 `raise ValueError`。
2. **DPI**：打包后仍是 per-monitor aware。本机 100% 缩放无偏移；接收方若 125%/150%，框选与点击会随坐标增大而偏移（所有者已决定暂不处理）。
3. **日志不落盘**（所有者已决定暂不处理）：`--noconsole` 之后所有警告无处可见。

### ✅ 历史前置障碍：路径全部基于 `__file__`（**已解决**）

这是当初判定"不能打包"的核心理由，现已由 `paths.py` 解决（见 §8.1 #60）：

| 当时的问题 | 现在 |
|---|---|
| **① 用户数据会被写进临时目录** | `paths.data_dir()` 在 frozen 时返回 **exe 所在目录**，源码运行时返回项目根，可用环境变量 `VF_DATA_DIR` 覆盖 |
| **② 资源与数据未分离** | `paths.resource_root()`（只读，frozen 时 = `sys._MEIPASS`）与 `data_dir()`（可写）分开——`checkbox_*.svg` 随程序打包，模板 PNG 在可写目录 |
| 路径分散在三处、都用 `os.path.dirname(__file__)` | 全部收敛到 `paths.py`；`tests/test_paths.py` 有静态守卫：**只有 `paths.py` 允许出现 `__file__`** |

**实测证据**：打包后的应用日志框自报
`[打包运行] 资源目录=...\VisionFlow_Automator\_internal；数据目录=...\VisionFlow_Automator`，
且启动时**不写任何 JSON**（只读加载，符合设计）。
